  1. FRHICommandListExecutor::FSubmitState::Submit 是否触发了绘制命令提交?

  是的。 这是 RHI 层把"已经翻译完的平台命令包"递给底层 dynamic RHI 的最后一道关卡。

  3. 下层 ProcessSubmissionQueue 怎么工作？

  GDynamicRHI->RHISubmitCommandLists(...) (D3D12 路径) 最终把每个 context 上的 FD3D12Payload* 数组喂给
  FD3D12DynamicRHI::SubmitPayloads:

  Source\Runtime\D3D12RHI\Private\D3D12Submission.cpp:330:

  void FD3D12DynamicRHI::SubmitPayloads(TArray<FD3D12Payload*>&& Payloads)
  {
      if (Payloads.Num())
          PendingPayloadsForSubmission.Enqueue(new TArray<FD3D12Payload*>(MoveTemp(Payloads)));

      if (SubmissionThread)
          SubmissionThread->Kick();          // SetEvent 唤醒 submission 线程
      else
          // 单线程退化路径: 当前线程直接跑
          while (EnumHasAnyFlags(ProcessSubmissionQueue().Status, EQueueStatus::Processed)) {}

      ProcessInterruptQueueUntil(nullptr);    // 顺便 pump 中断队列
  }

  submission 线程的循环 (D3D12Submission.cpp:121) 等 Event，每次醒来反复跑 ProcessSubmissionQueue 直到没活，再睡:

  do { Result = (RHI->*QueueFunc)(); }
  while (EnumHasAllFlags(Result.Status, EQueueStatus::Processed));
  WaitForSingleObject(Event, Result.WaitTimeout);

  ProcessSubmissionQueue (D3D12Submission.cpp:372) 的核心循环:

  do {
      bProgress = false;

      // 1. 把 lock-free 队列里的全部 payload 拆到 per-queue 的有序队列
      while (PendingPayloadsForSubmission.Dequeue(Array)) {
          for (auto* P : *Array) P->Queue.PendingSubmission.Enqueue(P);
          delete Array;
      }

      // 2. 遍历所有 queue (跨 device / pipe)
      ForEachQueue([&](FD3D12Queue& Q) {
          while (auto* P = Q.PendingSubmission.Peek()) {
              // 等待解析: 把每个 SyncPointsToWait 转换成 D3D12 fence wait
              for (...; ...; ++P->SyncPointsToWait.Index) {
                  if (!SyncPoint->ResolvedFence.IsSet())
                      return;                 // 该 SyncPoint 还没被任何 Signal payload 走过
                                              // submission thread —— 等下一轮再试
                  P->AddQueueFenceWait(SyncPoint->ResolvedFence->Fence,
                                       SyncPoint->ResolvedFence->Value);
              }
              Q.PendingSubmission.Dequeue();
              Q.PayloadToSubmit = P;
              // 累积 occlusion / pipeline-stats / timestamp queries 等
              AccumulateQueries(...);
          }

          Q.FinalizePayload(false, PayloadsToHandDown);   // ExecuteCommandLists + Signal
                                                         // 并写入 SyncPoint->ResolvedFence
      });
  } while (bProgress);

  FlushPayloads();
  if (InterruptThread && bKickInterruptThread) InterruptThread->Kick();

  FinalizePayload 是真正调 ID3D12CommandQueue::ExecuteCommandLists + Signal(fence, value) 的地方，并把
  SyncPoint->ResolvedFence = { Fence, Value } 填上，这样后面所有依赖该 SyncPoint 的 payload 就能解析为具体的 fence wait。

  双线程模型:
  - Submission 线程——只跟 D3D12 队列打交道 (ExecuteCommandLists / Signal / 跨队列 Wait)。
  - Interrupt 线程——ProcessInterruptQueue 轮询 Fence->GetCompletedValue()，对完成的 payload:
  for (FD3D12SyncPointRef& SyncPoint : Payload->SyncPointsToSignal)
      if (SyncPoint->GraphEvent)
          SyncPoint->GraphEvent->DispatchSubsequents();   // 解锁 CPU 等待方

  4. FD3D12Payload 的设计目的

  Source\Runtime\D3D12RHI\Private\D3D12Submission.h:187 (FD3D12PayloadBase):

  它是 某一个 GPU queue 上的一个最小可提交单元 ——
  把"等谁、做什么、给谁发信号、收尾要释放什么"这套一次提交的全部状态打成一个值类型对象。字段分组很说明问题:

  ┌───────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │   阶段    │                                      字段                                       │
  ├───────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ 绑定      │ FD3D12Queue& Queue (哪个 device + queue type)                                   │
  ├───────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ Wait      │ SyncPointsToWait (跨队列同步)、QueueFencesToWait、ManualFencesToWait            │
  ├───────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ 预执行    │ PreExecuteCallback、ReservedResourcesToCommit                                   │
  ├───────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ Execute   │ CommandListsToExecute (一组 FD3D12CommandList*)                                 │
  ├───────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ Signal    │ SyncPointsToSignal、ManualFencesToSignal、CompletionFenceValue、SubmissionEvent │
  ├───────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ Profiling │ Timing、BreadcrumbRange、BreadcrumbAllocators、EventStream                      │
  ├───────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ Cleanup   │ AllocatorsToRelease、BatchedObjects                                             │
  ├───────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ 标志      │ bAlwaysSignal、bSubmitted                                                       │
  └───────────┴─────────────────────────────────────────────────────────────────────────────────┘

  设计上的几个关键点:
  1. 单 queue、单方向——一个 payload 不跨队列。跨队列同步通过 SyncPoint 表达。
  2. 流水化——它的字段顺序就是 submission 线程处理时的 阶段 顺序 (Wait → PreExecute → UpdateReservedResources → Execute →
  Signal → Cleanup)。HasXxxWork() 帮 submission 线程跳过空阶段。
  3. 生产 / 消费解耦——producer (render/RHI 线程) 只填字段，consumer (submission 线程) 只读。中间隔一个 lock-free 队列 +
  一个唤醒事件。
  4. 延迟资源回收——AllocatorsToRelease 放进 payload 里跟随 fence completion 一起在 interrupt 线程 释放，避免 GPU
  还在用就被回收。
  5. 平台多态——FD3D12PayloadBase 是基类，WindowsD3D12Submission.h 里的 FD3D12Payload final : FD3D12PayloadBase 只为标
  final (避免虚函数间接调用代价，纯实现细节)。

  5. FD3D12SyncPoint 怎么处理同步

  D3D12Submission.h:66:

  ┌─────────────┬────────────────────────────┬──────────────────────────────────────────────────────────────────────┐
  │    角色     │            时机            │                                 动作                                 │
  ├─────────────┼────────────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ Producer    │ 录制时                     │ FD3D12SyncPoint::Create()，挂到一个 payload 的                       │
  │ (RHI 线程)  │                            │ SyncPointsToSignal、挂到另一个 payload 的 SyncPointsToWait           │
  ├─────────────┼────────────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │             │                            │ 选定 queue 上单调递增的 fence value，写入                            │
  │ Submission  │ FinalizePayload 内         │ SyncPoint->ResolvedFence，调 Signal(fence, value)。等待方 payload 在 │
  │ 线程        │                            │  ProcessSubmissionQueue 里读到这个 ResolvedFence 才能转换成          │
  │             │                            │ ID3D12CommandQueue::Wait(fence, value)                               │
  ├─────────────┼────────────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ Interrupt   │ 轮询                       │ 一旦完成，对每个 SyncPointsToSignal 调                               │
  │ 线程        │ fence->GetCompletedValue() │ GraphEvent->DispatchSubsequents()，CPU 等待方被解锁                  │
  └─────────────┴────────────────────────────┴──────────────────────────────────────────────────────────────────────┘

  CPU Wait (D3D12Submission.cpp:975):
  void FD3D12SyncPoint::Wait() const {
      if (!GraphEvent->IsComplete())
          FD3D12DynamicRHI::GetD3DRHI()->ProcessInterruptQueueUntil(GraphEvent);  // 一边等一边帮 pump
      check(GraphEvent->IsComplete());
  }
  注意它不是裸 WaitForSingleObject——而是让等待线程自己代跑 ProcessInterruptQueue，直到 本 GraphEvent
  完成。这是个典型的"等待时不闲着，反正得有人 pump 中断队列"的设计。

  重要: SyncPoint 是 一次性 的 (one-shot)，引用计数管理生命周期 (TRefCountPtr<FD3D12SyncPoint> =
  FD3D12SyncPointRef)。还有个 lock-free MemoryPool 池化 SyncPoint 的内存，热路径上避免 malloc。

  6. 怎么利用 FGraphEvent

  FD3D12SyncPoint 直接持有一个 FGraphEventRef，作用是把 GPU 完成事件转化为可被任务图等待的对象:

  - CPU 阻塞等待——SyncPoint->Wait() → GraphEvent->IsComplete() / Wait()。
  - 任务依赖等待——上层 (例如 RDG) 可以把 SyncPoint->GetGraphEvent() 喂给 FGraphEventArray Prerequisites，让某个任务在 GPU
   完成后自动启动。
  - 发信号——只在 interrupt 线程上的 ProcessInterruptQueue 中调 GraphEvent->DispatchSubsequents()，把所有挂着的
  subsequents 解锁。

  FlushCommands 这种调用还会额外 new 一个 SubmissionEvent = FGraphEvent::CreateGraphEvent()，挂在 payload 的
  SubmissionEvent 字段上——submission 线程在 FinalizePayload 里调 DispatchSubsequents()。这个事件表示**"已经送到 D3D12
  队列"**(注意不是"GPU 已经做完")，跟 SyncPoint 的 GraphEvent (代表"GPU 已经完成") 是两种不同语义的事件:

  // D3D12CommandContext.cpp:619 FlushCommands
  SyncPoint = Create(GPUAndCPU, ...);   SignalSyncPoint(SyncPoint);    // GPU 完成事件
  SubmissionEvent = CreateGraphEvent(); GetPayload(Signal)->SubmissionEvent = ...; // submission 完成事件
  SubmitPayloads(...);
  if (SyncPoint)         SyncPoint->Wait();           // 用 SyncPoint 的 GraphEvent
  if (SubmissionEvent)   SubmissionEvent->Wait();     // 用裸 GraphEvent

  7. FGraphEvent 实现原理 (UE 5.x 新实现)

  重大变化: 在新版引擎里 FGraphEvent 已经不是独立类了。Source\Runtime\Core\Public\Async\TaskGraphFwd.h:

  class FBaseGraphTask;
  using FGraphEvent    = FBaseGraphTask;
  using FGraphEventRef = TRefCountPtr<FBaseGraphTask>;

  FBaseGraphTask (TaskGraphInterfaces.h:466) 又只是 UE::Tasks::Private::FTaskBase
  (Source\Runtime\Core\Public\Tasks\TaskPrivate.h) 的一层薄壳。所谓 DispatchSubsequents / DontCompleteUntil / Wait
  全部是兼容旧 API 的 inline shim:

  void DispatchSubsequents(...) { Unlock(...); }         // = TryLaunch(0)
  void DontCompleteUntil(FGraphEventRef Nested) {
      if (IsTaskEvent()) AddPrerequisites(*Nested);      // 事件无法嵌套，降级为前驱
      else               AddNested(*Nested);
  }
  bool IsComplete() const { return IsCompleted(); }

  CreateGraphEvent() 实际 new 出来的是 FGraphEventImpl，它把 ExtendedPriority 设成 TaskEvent，没有任务体 (ExecuteTask 是
  checkNoEntry)，从 TLockFreeFixedSizeAllocator_TLSCache 池子里拿内存。

  核心数据结构 (FTaskBase，TaskPrivate.h)

  std::atomic<uint32> RefCount;                               // 自管引用计数，配 TRefCountPtr
  std::atomic<uint32> NumLocks { 1 };                         // 见下文双重含义
  static constexpr uint32 ExecutionFlag = 0x80000000;         // 状态位

  FPrerequisites<TInlineAllocator<1>> Prerequisites;          // 我依赖谁
  FSubsequents<TInlineAllocator<1>>  Subsequents;             // 谁依赖我
  LowLevelTasks::FTask LowLevelTask;
  FEventCount StateChangeEvent;

  FSubsequents (TaskPrivate.h:770) 已经不是 TLockFreePointerList，改成 UE::FMutex 保护的 TArray<FTaskBase*,
  TInlineAllocator<1>> + std::atomic<bool> bIsClosed:

  bool PushIfNotClosed(FTaskBase* NewItem) {
      if (bIsClosed.load(std::memory_order_acquire)) return false;    // 快路径无锁
      UE::TUniqueLock Lock(Mutex);
      if (bIsClosed) return false;
      Subsequents.Emplace(NewItem);
      return true;
  }
  TArray<FTaskBase*, ...> Close() {
      UE::TUniqueLock Lock(Mutex);
      bIsClosed = true;
      return MoveTemp(Subsequents);
  }
  - TInlineAllocator<1>——绝大多数任务只有 1 个 subsequent，零堆分配。
  - 已 close 的快路径只做一个 acquire load，没有锁竞争。

  NumLocks 的双重身份 (这是这套实现最巧妙的地方)

  - 执行前: 计 未完成前驱数。AddPrerequisites 增、前驱完成后 TryUnlock 减。减到 0 时调 Schedule。
  - 一旦 TrySetExecutionFlag 把高位 ExecutionFlag 置上 (代表"开始执行了")，同一个原子计数器立刻改成数 未完成嵌套任务
  (AddNested 增、嵌套完成后 TryUnlock 减)。减回 ExecutionFlag (即真正剩 0 个嵌套) 时调 Close()。

  bool TryUnlock(bool& bWakeUpWorker) {
      uint32 Prev = NumLocks.fetch_sub(1, std::memory_order_acq_rel);
      if (Prev < ExecutionFlag) {        // 还在等前驱阶段
          if (Prev - 1 == 0) Schedule(bWakeUpWorker);   // 或 Inline 直接 TryExecuteTask，或 TaskEvent 直接 Close
      } else {                            // 已在执行，等嵌套
          if (Prev - 1 == ExecutionFlag) { Close(); Release(); }
      }
  }

  "解锁后继" 的核心 (Close，TaskPrivate.h:545)

  void Close() {
      bool bWakeUpWorker = (ExtendedPriority == TaskEvent);   // 普通任务首个后继可塞本地队列
      for (FTaskBase* S : Subsequents.Close())
          S->TryUnlock(bWakeUpWorker);                        // 引用按值传递更新 → 之后的塞全局队列
      if (GetPipe()) ClearPipe();
      ReleasePrerequisites();
      StateChangeEvent.NotifyWeak();      // 唤醒 Wait() 等任务回缩 (retraction)
  }
  首个 subsequent 走 本地队列 (避免全局队列 + 一次 worker 唤醒)，其余统一进全局队列并唤醒一个 worker——典型的
  work-stealing 调度优化。

  DispatchSubsequents() 完整生命周期

  1. 外部调 event->DispatchSubsequents() ≡ Unlock()。
  2. Unlock 对 TaskEvent 类型先 AddRef() 保活，再 TryLaunch(0)。
  3. TryLaunch 内部最终走到 TryUnlock。NumLocks 减到 0 且是 TaskEvent → TrySetExecutionFlag (CAS 把 ExecutionFlag 置位)
  成功 → 直接 Close()。
  4. Close() 把 Subsequents 队列原子地"关门 + 取出"，对每个后继调 TryUnlock。某个后继如果 NumLocks 减到 0，就要么直接执行
   (Inline) 要么 Schedule 入低层任务系统。

  引用计数

  - 不再继承 FRefCountedObject，而是 FTaskBase 自己的 std::atomic<uint32> RefCount + 自管 AddRef/Release + delete this。
  - 一对 AddRef: AddPrerequisites 给前驱加 ref (跨依赖边保活)、Unlock 给 TaskEvent 加 ref (触发后才被系统持有)。
  - 对应 Release 在 Close()/ReleaseInternalReference() 里成对释放。
  - TRefCountPtr<FBaseGraphTask> (= FGraphEventRef) 调的就是上面那对。

  与 UE::Tasks::FTaskEvent 的关系

  FTaskEvent (Tasks/Task.h) 是新公开 API，包装 FTaskEventBase (派生 FTaskBase，ExtendedPriority = TaskEvent)。和
  FGraphEvent/FGraphEventImpl 几乎一一对应，只是它的 Trigger() 用 std::atomic<bool> TaskTriggered.exchange(true)
  保证可重复触发也只生效一次:

  bool Trigger(uint64) {
      if (TaskTriggered.exchange(true, std::memory_order_relaxed)) return false;
      AddRef();
      return TryLaunch(...);
  }
  旧的 DispatchSubsequents 没有这个幂等性保护——一个 FGraphEvent 只允许 dispatch 一次。

  ---
  2. 怎么获取任务？

  数据结构：FD3D12Queue::PendingInterrupt — 一个 TSpscQueue<FD3D12Payload*>（单生产者单消费者队列）。

  生产者是 Submission Thread 的 FlushBatchedPayloads（D3D12Submission.cpp:890）：

  for (FD3D12Payload* Payload : PayloadsToSubmit)
  {
      Payload->Queue.PendingInterrupt.Enqueue(Payload);   // 入队
      // ... Wait / PreExecute / ExecuteCommandLists / Signal ...
  }
  // 全部处理完后
  for (FD3D12Payload* Payload : PayloadsToSubmit)
      Payload->bSubmitted = true;   // 所有权移交给 Interrupt Thread

  入队完成后 ProcessSubmissionQueue 末尾调 InterruptThread->Kick()（即 SetEvent(Event)）唤醒 Interrupt Thread。

  ---
  3. 怎么执行？ — ProcessInterruptQueue 完整流程

  D3D12Submission.cpp:1101，核心结构：

  ProcessInterruptQueue()
  ├── ForEachQueue(&)                          // 遍历所有 device 的所有 queue
  │   └── while (PendingInterrupt.Peek())      // 逐个处理该 queue 上的 payload
  │       ├── 检查 bSubmitted 标志
  │       ├── GetCompletedValue() 问 GPU fence
  │       ├── 未完成 → SetEventOnCompletion + GPU hang 检测 → break
  │       └── 已完成 → 解析 query / signal SyncPoint / delete payload
  └── 全局 GPU crash 检测

  3.1 检查 payload 是否可以处理

  if (!Payload->bSubmitted)
      break;   // Submission Thread 还在操作这个 payload，不能碰

  bSubmitted 是 std::atomic<bool>，是一个无锁的所有权移交：Submission Thread 先入队，完成所有 D3D12 操作后设为
  true；Interrupt Thread 只在 true 时才处理。

  3.2 Fence Polling — 判断 GPU 是否完成

  uint64 CompletedFenceValue = CurrentQueue.Fence.D3DFence->GetCompletedValue();

  直接问 D3D12 驱动 "这个 queue 上的 fence 走到哪个值了？" 然后与 payload 的 CompletionFenceValue 比较。

  3.3 GPU 未完成时的处理

  if (CompletedFenceValue < Payload->CompletionFenceValue)
  {
      // 注册 D3D12 驱动回调：GPU 走到 CompletionFenceValue 时自动 SetEvent
      if (InterruptThread && !CurrentQueue.Fence.bInterruptAwaited)
      {
          CurrentQueue.Fence.D3DFence->SetEventOnCompletion(
              Payload->CompletionFenceValue,
              InterruptThread->Event     // 复用线程的 Win32 Event！
          );
          CurrentQueue.Fence.bInterruptAwaited = true;
      }

      // GPU hang 超时检测（默认 5 秒）
      // ...

      break;  // 跳出这个 queue 的循环，去检查其他 queue
  }

  关键点：SetEventOnCompletion 复用了 Interrupt Thread 的 Event。所以 Interrupt Thread 不需要 busy-wait，而是：

  1. 第一轮发现 GPU 没完成 → 注册驱动回调
  2. 回到 FD3D12Thread::Run 的 WaitForSingleObject(Event, WaitTimeout) 睡下
  3. GPU 完成 → D3D12 驱动自动 SetEvent → 线程醒来
  4. 下一轮 GetCompletedValue() >= CompletionFenceValue → 进入完成处理

  GPU hang 检测也在这个分支里：如果超时（默认 5 秒）GPU 还没完成，调用 HandleGpuTimeout。

  3.4 GPU 完成后的处理

  CurrentQueue.Fence.bInterruptAwaited = false;
  CurrentQueue.PendingInterrupt.Dequeue();

  // 1. 解析 Query 结果 (Occlusion / PipelineStats / Timestamps)
  //    把 GPU 写入的 query buffer 数据拷贝到上层 Target 指针

  // 2. GPU Profiler event stream 收集

  // 3. 切换 Timing struct (per-frame 分界)

  // 4. ★ Signal 所有 SyncPoint 的 GraphEvent ★
  for (FD3D12SyncPointRef& SyncPoint : Payload->SyncPointsToSignal)
  {
      if (SyncPoint->GraphEvent)
          SyncPoint->GraphEvent->DispatchSubsequents();
      // 这会解锁所有在该 SyncPoint 上 Wait() 的 CPU 线程
  }

  // 5. delete Payload（析构函数回收 CommandAllocator 等）
  delete Payload;

  5. 无 Interrupt Thread 的退化路径

  当 D3D12_USE_INTERRUPT_THREAD = 0 时，由调用 SyncPoint::Wait() 的线程自己代劳：

  void FD3D12DynamicRHI::ProcessInterruptQueueUntil(FGraphEvent* GraphEvent)
  {
      if (InterruptThread)
      {
          // 有专用线程 → 直接等
          if (GraphEvent && !GraphEvent->IsComplete())
              GraphEvent->Wait();
      }
      else
      {
          // 没有专用线程 → 当前线程自己 pump 中断队列
      Retry:
          if (InterruptCS.TryLock())
          {
              FProcessResult Result;
              do { Result = ProcessInterruptQueue(); }
              while (GraphEvent
                  ? !GraphEvent->IsComplete()           // 等指定事件完成
                  : EnumHasAllFlags(...));              // 或 pump 到没活
              InterruptCS.Unlock();
          }
          else if (GraphEvent && !GraphEvent->IsComplete())
          {
              FPlatformProcess::SleepNoStats(0);  // 让出时间片，重试
              goto Retry;
          }
      }
  }

  SyncPoint::Wait() 直接调的就是这个函数——没有专用 Interrupt Thread 时，等待线程一边 polling fence
  一边帮着处理中断队列，不做无用等待。

FRDGPass 功能定义

  FRDGPass 是所有 Render Graph Pass 的基类，定义了以下核心能力：

  1. Pass 元数据

  成员: Name
  类型: FRDGEventName
  作用: GPU 调试/性能分析用的 Pass 名称
  ────────────────────────────────────────
  成员: ParameterStruct
  类型: FRDGParameterStruct
  作用: 绑定的 shader 参数结构体
  ────────────────────────────────────────
  成员: Flags
  类型: ERDGPassFlags
  作用: 标记 GPU 工作类型（Raster/Compute/AsyncCompute/Copy 等）
  ────────────────────────────────────────
  成员: TaskMode
  类型: ERDGPassTaskMode
  作用: 执行模式（Inline/Await/Async）
  ────────────────────────────────────────
  成员: Pipeline
  类型: ERHIPipeline
  作用: 所属管线（Graphics / AsyncCompute）

  2. 三种执行路径 (ERDGPassTaskMode)

  ┌──────────────────────────────────────────────────────────────────────┐
  │                    ERDGPassTaskMode 执行路径                         │
  ├──────────┬───────────────────────────────────────────────────────────┤
  │  Inline  │ 必须在渲染线程上内联执行。lambda 接收 FRHICommandListImmediate │
  │  Await   │ 可以在并行 task 中执行，在 FRDGBuilder::Execute() 结尾 await   │
  │  Async   │ 可以在并行 task 中执行，不自动 await，需手动同步               │
  └──────────┴───────────────────────────────────────────────────────────┘

  TaskMode 的自动推导规则（在 TRDGLambdaPass::ExecuteLambdaTraits 中）：
  - Lambda 参数是 FRHICommandListImmediate& → Inline
  - Lambda 参数是 FRHICommandList& 且无 FRDGAsyncTask 标记 → Await
  - Lambda 参数带 FRDGAsyncTask 前缀 → Async

  3. Pass 状态位（控制编译/执行行为）

  bSkipRenderPassBegin / bSkipRenderPassEnd   ← Render Pass 合并控制
  bAsyncComputeBegin / bAsyncComputeEnd       ← Async Compute 区间首尾标记
  bGraphicsFork / bGraphicsJoin              ← Graphics 与 AsyncCompute 同步点
  bRenderPassOnlyWrites                       ← 仅在 Render Pass 内写
  bSentinel                                   ← 哨兵 Pass（Prologue/Epilogue）
  bDispatchPass                               ← 是否为 Dispatch Pass
  bDispatchAfterExecute                       ← 执行后刷新到 RHI 线程
  bCulled                                     ← 被剔除
  bParallelExecuteBegin / bParallelExecuteEnd ← 并行执行区间标记
  bParallelExecute                            ← 当前正在并行执行

  4. Pass 子类体系

  FRDGPass (基类)
  ├── TRDGLambdaPass<Param, Lambda>     ← 最常用：lambda 执行体
  │   └── TRDGEmptyLambdaPass<Lambda>   ← 无参数版本
  ├── FRDGDispatchPass                  ← 并行 CommandList 派发
  │   └── TRDGDispatchPass<Param, Lambda>
  └── FRDGSentinelPass                  ← Prologue/Epilogue 哨兵

  5. 屏障（Barrier）管理

  每个 Pass 管理一组 split barrier batch：

  Prologue:  PrologueBarriersToBegin → PrologueBarriersToEnd
  Epilogue:  EpilogueBarriersToBeginForGraphics
             EpilogueBarriersToBeginForAsyncCompute
             EpilogueBarriersToBeginForAll
             → EpilogueBarriersToEnd

  Execute() 的完整执行流程

  FRDGBuilder::Execute()
  │
  ├── 1. FlushSetupQueue()          ← 刷新异步 Setup 队列
  │
  ├── 2. Compile()                  ← 编译阶段
  │   ├── SetupPassResources()      ← 为每个 Pass 建立资源跟踪
  │   ├── Culling                   ← 从 EpiloguePass 反向遍历，剔除无用 Pass
  │   ├── CompilePassBarriers()     ← 编译所有 Pass 的 Barrier
  │   └── CollectPassBarriers()     ← 收集并创建 RHI Transition
  │
  ├── 3. Resource Allocation
  │   ├── CollectAllocations/Deallocations  ← 按生命周期分配/回收资源
  │   ├── AllocatePooledBuffers/Textures    ← 分配池化资源
  │   ├── AllocateTransientResources        ← 分配瞬态资源
  │   ├── CreateViews                       ← 创建 SRV/UAV
  │   ├── CreateUniformBuffers              ← 创建 Uniform Buffer
  │   └── SubmitBufferUploads               ← 提交 Buffer 上传
  │
  ├── 4. ExecutePasses              ← 执行阶段（核心循环）
  │   │
  │   ├── if (bInitialAsyncComputeFence)
  │   │   └── Insert AsyncCompute→Graphics fence
  │   │
  │   ├── for each Pass in [Prologue .. Epilogue]:
  │   │   │
  │   │   ├── if (bCulled) → skip
  │   │   │
  │   │   ├── if (bParallelExecute) ──── 并行路径
  │   │   │   ├── if (bDispatchPass)
  │   │   │   │   └── Wait CommandLists → QueueAsyncCommandListSubmit
  │   │   │   └── else if (bParallelExecuteBegin)
  │   │   │       └── Queue parallel pass set command list
  │   │   │
  │   │   └── else ───────────────────── 串行路径
  │   │       └── ExecuteSerialPass(RHICmdList, Pass)
  │   │           ├── ExecutePassPrologue()  ← 提交 Barrier、Begin RenderPass
  │   │           ├── ExecutePass()          ← 执行 lambda
  │   │           └── ExecutePassEpilogue()  ← End RenderPass、提交 Barrier
  │   │
  │   └── FlushParallel()            ← 刷新所有排队的并行 CommandList
  │
  ├── 5. Wait ParallelExecute.TasksAwait  ← 等待 Await 模式的并行任务
  │
  ├── 6. Resource Extraction         ← 提取输出资源到外部
  │
  └── 7. PostExecuteCallbacks        ← 执行后回调

  ---
  一、Nanite 整体架构

  Nanite 不是"自动 LOD 系统"，而是"离线预构建出一棵 DAG，运行时每帧在 GPU 上对 DAG 做 cut"。各子系统的职责：

  ┌────────────────────────────┬────────────────────────────────────────────────────────────┬──────────────────────────────────────────────────────────┐
  │           子系统           │                            职责                            │                           位置                           │
  ├────────────────────────────┼────────────────────────────────────────────────────────────┼──────────────────────────────────────────────────────────┤
  │ Builder (CPU, 离线)        │ 从原始 mesh 构建 cluster + group + DAG，量化编码成 page    │ Source/Developer/NaniteBuilder/                          │
  ├────────────────────────────┼────────────────────────────────────────────────────────────┼──────────────────────────────────────────────────────────┤
  │ Resources (CPU/GPU)        │ 持久化的数据（page、hierarchy、cluster blob）              │ Source/Runtime/Engine/Public/Rendering/NaniteResources.h │
  ├────────────────────────────┼────────────────────────────────────────────────────────────┼──────────────────────────────────────────────────────────┤
  │ Streaming (GPU-driven)     │ page 按需 streaming 进显存，根 page 常驻                   │ Shaders/Private/Nanite/NaniteStreaming.ush               │
  ├────────────────────────────┼────────────────────────────────────────────────────────────┼──────────────────────────────────────────────────────────┤
  │ Culling / LOD Select (GPU) │ 每帧每个 view 在 hierarchy 上做 DAG cut + frustum/HZB cull │ NaniteClusterCulling.usf + NaniteCullingCommon.ush       │
  ├────────────────────────────┼────────────────────────────────────────────────────────────┼──────────────────────────────────────────────────────────┤
  │ SW/HW Rasterizer (GPU)     │ 小三角形软件光栅，大三角形硬件光栅                         │ NaniteRasterizer.usf                                     │
  └────────────────────────────┴────────────────────────────────────────────────────────────┴──────────────────────────────────────────────────────────┘

  Builder 这一侧的核心数据结构（来自 ClusterDAG.h）：

  class FCluster {           // DAG 节点 = ~128 三角形
      FVertexArray Verts;
      TArray<uint32> Indexes;
      FSphere3f LODBounds;       // 用来投影到屏幕计算 cut
      float LODError;            // 这一级的最大几何偏差（世界空间）
      int32 MipLevel;            // 在 DAG 中的层级
      uint32 GroupIndex;         // 我属于哪个 group（这个 group 锁住了我的边界）
      uint32 GeneratingGroupIndex; // 我被哪个 group 简化产生（我的 parent 锁住的边界来自这里）
  };

  struct FClusterGroup {     // 8–32 个 cluster 的绑定单元
      FSphere3f LODBounds;
      float ParentLODError;      // 简化后产生的误差
      TArray<FClusterRef> Children;
  };

  class FClusterDAG {
      TArray<FCluster> Clusters;
      TArray<FClusterGroup> Groups;
  };

  二、预处理流水线拆解

  入口 FBuilderModule::Build (NaniteBuilder.cpp:574)，调用链：

  Build
   └─ BuildIntermediateResources       // 阶段 ①–④
       ├─ PreprocessMesh               // 可选：displacement 自适应细分
       ├─ ClusterDAG.AddMesh           // 阶段 ①② 三角形→叶子 cluster
       └─ ClusterDAG.ReduceMesh        // 阶段 ③ DAG 层级构建（核心）
   ├─ BuildFallbackMesh                // 老GPU回退网格
   └─ Encode                           // 阶段 ④ 量化 + 切 page

  阶段 ①：构邻接图（AddMesh, ClusterDAG.cpp:21）

  - 用 FEdgeHash 并行哈希所有有向边（按位置哈希），找到反向匹配 → FAdjacency。
  - 大于 2 个三角形共享一条边的退化情况单独排序后处理，保证决定性（同样输入产出同样 DAG）。
  - FDisjointSet 把三角形按连通性合并，partition 时同一连通块倾向于聚到一起。

  阶段 ②：把三角形切成 ~128 三角形的叶子 Cluster

  FGraphPartitioner Partitioner(NumTriangles, FCluster::ClusterSize - 4, FCluster::ClusterSize);
  //                                          124, 128
  Partitioner.BuildLocalityLinks(...);
  Partitioner.PartitionStrict(Graph, !bSingleThreaded);   // 调用 METIS

  - FGraphPartitioner 实质是 METIS 多级递归二分。
  - 邻接图的"权重"鼓励：① 共享边的三角形聚到一起（连通性）② locality link（空间局部性）。
  - 输出 Partitioner.Ranges，每个 range 是一个 cluster 的三角形索引区间。
  - 叶子 cluster 标记：Cluster.EdgeLength *= -1（负数 = 叶）。

  阶段 ③：DAG 层级构建（ReduceMesh，灵魂）

  这是 Nanite 的灵魂循环。ClusterDAG.cpp:430 起：

  while (LevelClusters.Num() > 1):
     // ③.a 找跨 cluster 的"外部边"，建 cluster 之间的邻接图
     FindAdjacentClusters(...)

     // ③.b 把 cluster 分组（8 ≤ size ≤ 32），三角形组 + voxel组分开
     GroupTriangleClusters(TriClusters, NumExternalEdges)   // 又一次 METIS
     GroupVoxelClusters(VoxelClusters)                       // Morton 排序 + 贪心配对合并

     // ③.c 每个 group 独立并行简化
     ParallelFor each group:
         ReduceGroup(...):
             Merged   = FCluster(DAG, Group.Children)        // 合并 group 内所有 cluster
             SimplifyError = Merged.Simplify(targetNumTris)  // QEM-based 边折叠，targetNumTris ≈ NumParents * 126
             SplitCluster<FGraphPartitioner>(Merged, ...)    // 把简化后的 mesh 重新切回 ~128 三角形的 parent clusters
             对每个 parent cluster 写入:
                 LODBounds         = Group.LODBounds         // 同组共用！
                 LODError          = Group.ParentLODError    // 同组共用！
                 GeneratingGroupIndex = GroupIndex

     LevelClusters = 这一层产生的所有 parent clusters

  这里有三个至关重要的不变性（决定为什么 Nanite 能做连续 LOD）：

  不变性 1：Group 内的所有 cluster 在 LOD 决策上"同生共死"
  同一 group 的所有 children → 一起被选中作为高细节，或者一起被它们生成的 parent 替换。这是因为简化只在 group 内部进行，group 与 group 之间共享的边永远不会被折叠。

  不变性 2：Group 边界 = 不能折叠的边
  看 GroupTriangleClusters 的权重计算（ClusterDAG.cpp:312）：
  bool bSiblings = Cluster.GeneratingGroupIndex == OtherCluster.GeneratingGroupIndex;
  Partitioner.AddAdjacency(Graph, OtherClusterRefIndex,
                           NumSharedEdges * (bSiblings ? 12 : 16) + 4);
  sibling 比非 sibling 权重小（12 vs 16）→ METIS 倾向于把 sibling 切到不同 group。
  为什么？这样上一轮的 group 边界（被锁住的边）这一轮就能落进新 group 内部被折叠掉。否则越往上层 锁死的边越多，简化会停滞。

  不变性 3：Parent.LODError ≥ max(Children.LODError)，单调递增
  在 ReduceGroup 末尾：Group.ParentLODError = max(child errors, SimplifyError)，并把这个值写回每个 parent cluster。这样 GPU 端做 cut 时只需做单调比较，不需要全局搜索。

  构建终止条件

  循环到 LevelClusters.Num() == 1 退出，最后一个 cluster 是 root；额外塞一个 RootClusterGroup，ParentLODError = 1e10f（永远不可能被替换为更粗的版本）。

  阶段 ④：量化与编码（Encode/ 目录）

  按顺序的 pass：

  NaniteEncode.cpp           主驱动
  ├─ NaniteEncodeConstrain   位置/属性量化范围约束
  ├─ NaniteEncodeVertReuseBatch  顶点复用批次
  ├─ NaniteEncodeMaterial    material range 编码
  ├─ NaniteEncodeTriStrip    三角形 strip 化（GPU 软光栅友好）
  ├─ NaniteEncodeHierarchy   构建 BVH4 hierarchy node（GPU traversal 用的，不是 cluster DAG 本身）
  ├─ NaniteEncodePageAssignment   把 cluster 装进 128KB page
  └─ NaniteEncodeFixup       page 间引用 fixup

  关键点：
  - 位置量化：每 cluster 单独的 QuantizedPosStart/Precision/Bits，按 cluster 局部 bound 自适应。
  - Hierarchy ≠ DAG：编码阶段会重新构建一个 4-ary BVH（FHierarchyNodeSlice，每个 node 含 4 个 child）用于 GPU 遍历；DAG 的拓扑信息被烘焙到 node 的 MaxParentLODError 字段里。
  - Page 装箱：以 DAG 的 group 为最小不可分单位塞进 page，相关 cluster 会进同一 page（streaming 时连贯）。

  三、LOD 选择机制（运行时）

  GPU 上每帧、每个 view 独立做 DAG cut。核心循环在 NaniteClusterCulling.usf 的 hierarchy traversal（参考 NaniteStreamOut.usf:447 的简化版，逻辑相同）：

  // 自顶向下遍历 BVH4 hierarchy
  bool ShouldVisitChild(FHierarchyNodeSlice node, bool bVisible) {
      return bVisible && (CutError < node.MaxParentLODError);
      //                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
      //  如果允许的最大像素 error 都比这一层的 ParentError 还小，
      //  说明这一层还不够细 → 继续向下
  }

  // 到达 cluster 叶子
  void ProcessCluster(...) {
      bool bSmallEnoughToDraw = CutError > Cluster.LODError;
      //   到这一层已经足够细了 → 画这个 cluster
  }

  CutError 是怎么算的？

  CutError 不是常数，是用 LODBounds (世界空间球) 投影到屏幕、得到允许的世界空间 deviation：
  - NaniteCullingCommon.ush 里把 sphere bound 经 LOD transform 变换、按视图距离/焦距计算屏幕投影半径。
  - 通常对应"屏幕上 1 像素 ≈ 多少世界空间长度"。

  为什么能连续 LOD 而不出现裂缝？

  回到三个不变性：
  - 同组共生共死 → 一个 cluster 被选中作为 child，那它整个 group 的兄弟也一定被选中（因为它们 LODError 完全相同），它们之间共享的边永远是同一份顶点数据。
  - 跨组边界锁死 → 不同 group 共享的边在简化时没有被折叠过，无论这两个 group 各自被选到 child 还是 parent 级，相邻边的顶点位置都一致。
  - 单调误差 → 父级的 ParentLODError ≥ Group.ParentLODError ≥ children 任意 LODError，cut 沿 DAG 自上而下是良定义的：只要某个 view 在某 cluster 上 "够小了"，它在所有 ancestor 上一定 "更够小"。

  可视化心智模型：

                            [Root Cluster]                LODError = ∞
                                  |
                         ┌────────┴────────┐
                         │   Group L_top   │
                         │ ┌──┐ ┌──┐  ┌──┐│              ParentLODError 大
                         │ │P1│ │P2│  │Pn││  ← parents
                         │ └──┘ └──┘  └──┘│
                         └─┬─────┬─────┬──┘
                           │     │     │
                ┌──────────┴─────┴─────┴──────────┐
                │       Groups L_mid (8-32 cluster each)
                │   每组内部 cluster 边界被折叠
                │   组间边界保持不变
                └────────────...─────────────...──
                                │
                           leaf clusters (128 tri)         LODError 小

  每帧 GPU 在这张 DAG 上画一条水平线（cut）：相机近处 cut 落在底部（叶子），远处落在顶部（root）。同一物体不同部位的 cut 高度可以不同 → "每个 pixel 自适应 LOD" 的来源。
